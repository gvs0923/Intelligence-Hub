
# Engineering Intelligence Hub - Full Build Plan

A production-grade, 100% free/open-source RAG system built with Python, FastAPI, ChromaDB, Ollama, and Streamlit that ingests technical docs, code repos, and incident reports to provide contextual AI-powered answers for engineering teams — designed as an impressive AI/ML portfolio project.

## Objective

Build a **developer-focused RAG (Retrieval-Augmented Generation) system** called "Engineering Intelligence Hub" that:
1. Ingests multiple types of engineering knowledge (docs, code, incidents, architecture docs)
2. Indexes them with hybrid search (semantic + keyword)
3. Provides contextual, cited answers via a local LLM
4. Runs 100% locally with zero paid API dependencies
5. Demonstrates production-grade engineering practices worthy of a senior AI/ML resume

---

## What Makes This Resume-Worthy

This project will demonstrate:
- **RAG pipeline architecture** — chunking, embedding, retrieval, generation with citations
- **Hybrid search** — dense vector + BM25 lexical search with Reciprocal Rank Fusion (RRF)
- **AST-aware code chunking** — tree-sitter based, not naive line splitting
- **Multi-source ingestion** — GitHub repos, Markdown/Confluence docs, incident reports (JSON/CSV)
- **Evaluation framework** — Recall@K, MRR, NDCG with automated test harness
- **Production patterns** — async processing, caching, Docker deployment, CI/CD, logging, monitoring
- **Clean architecture** — modular, testable, well-documented Python code

### Phase 2: Ingestion Pipeline (Days 4-8)
**Goal:** Ingest docs, code repos, and incident reports into chunks

| Step | Task | Details |
|------|------|---------|
| 2.1 | **Text Chunker** | Sentence-aware splitting with configurable `chunk_size=512`, `overlap=50` tokens. Uses `langchain.text_splitter.RecursiveCharacterTextSplitter` |
| 2.2 | **Markdown Chunker** | Header-aware splitting — keeps H1/H2 sections together, preserves header hierarchy as metadata |
| 2.3 | **Code Chunker (tree-sitter)** | AST-based: extract functions, classes, methods as individual chunks. Fallback to 60-line sliding window for non-parseable files. Support Python, JS/TS, Java at minimum |
| 2.4 | **Markdown Ingester** | Walk directory, read `.md` files, apply markdown chunker, attach metadata (file path, title, section) |
| 2.5 | **GitHub Ingester** | Clone repo (GitPython), walk files (skip .git, node_modules, dist, etc.), apply code chunker, attach metadata (repo name, file path, language, function name) |
| 2.6 | **Incident Ingester** | Parse JSON/CSV incident reports. Fields: title, description, root_cause, resolution, severity, timestamp. Chunk long descriptions |
| 2.7 | **Ingestion orchestrator** | Async job runner: register source → trigger ingestion → track progress → report completion |
| 2.8 | **Sample data** | Create realistic sample data: 20+ Markdown docs, 1-2 small repos, 50+ incident reports |

### Phase 3: Indexing & Embedding (Days 9-11)
**Goal:** Embed chunks and store in ChromaDB + BM25 index

| Step | Task | Details |
|------|------|---------|
| 3.1 | **Embedder** | Wrapper around Ollama `nomic-embed-text` (768 dims). Batch embedding with rate limiting. Fallback to `sentence-transformers/all-MiniLM-L6-v2` (384 dims) if Ollama unavailable |
| 3.2 | **ChromaDB vector store** | Persistent ChromaDB with collections per source type. Store embeddings + metadata (source, file_path, chunk_type, language, timestamp) |
| 3.3 | **BM25 index** | Build `rank_bm25.BM25Okapi` index from chunk text. Serialize to disk with pickle. Rebuild on new ingestion |
| 3.4 | **Index Manager** | Orchestrate: chunk → embed → store in both ChromaDB + BM25. Incremental indexing (hash-based dedup — only re-embed changed files) |
| 3.5 | **Embedding cache** | Cache embeddings by content hash to avoid re-embedding identical chunks |

### Phase 2→3 Handoff: Chunk Text and Metadata Persistence

We also need to decide where chunk text and metadata are persisted. Currently the
pipeline saves only chunk references (`src/ingestion/pipeline.py:61-68`), so Phase 3
cannot simply read existing SQLite chunks and embed their text. This is a Phase 2→3
integration gap, rather than an explicit standalone Phase 2 requirement.

- [ ] Decide where chunk text and metadata are stored (e.g., `text` and `metadata`
      columns on the `Chunk` table, or a separate store)
- [ ] Update `IngestionPipeline` to save the chunk text and metadata along with the
      references
- [ ] Add a migration or schema update for existing databases
- [ ] Give Phase 3 a way to read saved chunks, with their text and metadata, for
      embedding without rerunning ingestion
- [ ] Add tests confirming chunk text and metadata survive a save-and-reload cycle

### Phase 4: Retrieval Pipeline (Days 12-16)
**Goal:** Hybrid retrieval with query rewriting and re-ranking

| Step | Task | Details |
|------|------|---------|
| 4.1 | **Dense retriever** | ChromaDB cosine similarity search, return top-20 candidates |
| 4.2 | **BM25 retriever** | Keyword search on BM25 index, return top-20 candidates |
| 4.3 | **Hybrid fusion (RRF)** | Reciprocal Rank Fusion: `score = Σ 1/(k + rank_i)` where k=60. Merge dense + BM25 results into unified ranked list |
| 4.4 | **Query rewriter** | Use Ollama LLM to expand/rewrite ambiguous queries. E.g., "auth broken" → "authentication failure error login service" |
| 4.5 | **Metadata filters** | Filter by source_type (docs/code/incidents), repository, language, date range, severity |
| 4.6 | **Re-ranker** | LLM-based listwise re-ranking: ask LLM to rank top-10 candidates by relevance to query. Returns final top-5 |
| 4.7 | **Confidence scoring** | Calculate retrieval confidence from similarity scores. If all scores < threshold (0.3), return "I don't have enough information" instead of hallucinating |

**Retrieval flow:**
```
User Query
    → Query Rewriter (LLM expands query)
    → Parallel: Dense Search (ChromaDB) + BM25 Search
    → RRF Fusion (merge + re-score)
    → Metadata Filter (apply user filters)
    → LLM Re-ranker (re-order top candidates)
    → Top-5 chunks with confidence scores
```

### Phase 5: Generation & Citations (Days 17-20)
**Goal:** Generate cited, grounded answers using local LLM

| Step | Task | Details |
|------|------|---------|
| 5.1 | **Ollama LLM client** | Async wrapper around Ollama Python SDK. Support streaming responses. Configurable model (llama3.2:3b default, mistral:7b for better quality) |
| 5.2 | **Prompt templates** | System prompt enforcing: answer only from context, cite sources with `[1]`, `[2]`, say "I don't know" when unsure |
| 5.3 | **Response builder** | Parse LLM output, extract citation references, map `[1]` → actual source (file path, line numbers). Return structured response with answer + sources |
| 5.4 | **Guardrails** | Hallucination check: verify every claim in the answer has a supporting chunk. Confidence score: low/medium/high based on retrieval scores |
| 5.5 | **Conversation memory** | Session-based chat history (last 5 turns). Context-aware follow-up handling |

**Prompt template (core):**
```
You are an Engineering Intelligence Assistant. Answer the question using ONLY 
the provided context. Cite every claim using [1], [2], etc.

Context:
[1] {source: "src/auth/login.py", lines: "45-67"}
{chunk_text_1}

[2] {source: "incident-report-2024-03-15.json", severity: "P1"}
{chunk_text_2}

...

If the context doesn't contain enough information, say: 
"I don't have enough information in the indexed sources to answer this."

Question: {user_query}
```

### Phase 8: Evaluation Framework (Days 28-30)
**Goal:** Rigorous evaluation to prove the system works

| Metric | Description |
|--------|-------------|
| **Recall@5** | % of queries where the correct answer chunk is in top 5 results |
| **Recall@10** | Same for top 10 |
| **MRR** (Mean Reciprocal Rank) | Average of 1/rank of first correct result |
| **NDCG@10** | Normalized Discounted Cumulative Gain |
| **Answer Faithfulness** | LLM-as-judge: does the answer only use info from retrieved context? |
| **Latency** | p50, p90, p95 query latency |

**Evaluation approach:**
1. Create a golden dataset: 50+ hand-labeled Q&A pairs mapped to expected source chunks
2. Run retrieval-only eval (Recall, MRR, NDCG) — measure retrieval quality
3. Run end-to-end eval (faithfulness, answer quality) — measure generation quality
4. Compare: dense-only vs BM25-only vs hybrid (RRF) to prove hybrid is better
5. Generate a markdown evaluation report with tables and charts

## Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Ollama performance on weak hardware | Default to llama3.2:3b (smallest). Allow config to switch models. Document minimum specs (8GB RAM) |
| ChromaDB scaling limits (>1M chunks) | For a portfolio project, unlikely to hit. Document limit. Could swap to pgvector if needed |
| Tree-sitter setup complexity | Pre-compile language grammars in Docker. Provide fallback line-based chunking |
